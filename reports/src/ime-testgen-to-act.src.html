IME test generator: analysis and ACT integration

This report covers riscv-ime-arch-tests at commit 46f3781, which tests the RISC-V Integrated Matrix Extension (IME). It reuses the terms of Report 1. Evidence tags: run observed in a run, code read in the source, inferred deduced but not observed.

Summary

  1. The generator. ime-test-gen is a Rust generator.
    • A compile-time test plan language feeds an exhaustive sweep over legal configurations: VLEN × λ (lambda, the IME tile parameter) × LMUL × SEW × signedness or rounding mode.
    • An independent Rust golden model computes every expected value at generation time.
    • The output is self-checking C++, which runs under QEMU user mode on Linux.
  2. The suite passes its own CI here. At VLEN=512, with the pinned SDK image, the CI reproduction passed. The generator emits 5372 tests, and every result matched ci/known-issues.txt. run
  3. The main difference from ACT is the source of expected values. ACT takes them from Sail at build time, and the generators emit only inputs. ime-test-gen embeds its own golden values, which are tuned to match QEMU's rounding. ACT measures coverage with covergroups. ime-test-gen enumerates configurations and has no coverage model.
  4. The intermediate representation (IR) is the integration point. For MACC (matrix multiply-accumulate) tests, the IR uses only target-neutral operations: tile load, tile zero, mmacc, tile store and compare. My proof of concept, ir2act.py, converts that IR into ACT test files. ACT built them with the IME Sail fork as reference model, and they ran on two DUTs. run
  5. The proof of concept found a model disagreement.
    • With the Sail fork as DUT, all 6 test files pass.
    • With the SDK QEMU as DUT, all 6 fail.
    • QEMU and the Rust golden model agree with each other; the Sail fork stores the C tile transposed.
    • QEMU and the Rust golden model match the specification. The Sail fork's vmtl.v and vmts.v index register elements without tile_reg_idx.
    run code
  6. Recommendation.
    • Bring-up: import the IR into testgen (option B).
    • Target: port the tests to native ACT testplans and coverpoints (option C).
    • Throughout: keep the Rust golden model as a differential check against Sail.
    Four blockers come first: the Sail version gate and schema, the UDB extension definitions, the experimental-extension flag, and the C-tile disagreement.
Orientation

1Terms

These terms add to the glossary of Report 1. A test in ime-test-gen is not the same thing as an ACT test file. This report says "IR test" for the generator's unit.

IME, Zvvm
The Integrated Matrix Extension. Its subextensions are Zvvmm (integer matrix multiply-accumulate), Zvvfmm (floating-point), Zvvmtls (tile load and store) and Zvvmttls (transposing tile load and store). The SDK compiler spells the extension zvmma in -march.
λ (lambda)
The tile parameter held in vtype bits 62:60. Encoding 001 means λ=1, 010 λ=2, and so on up to 111 λ=64. The line size of a tile is λ·LMUL.
Tile
A matrix operand held in a vector register group. In the asm lowering: A in v0, B in v8, accumulator C in v16.
W
The widening factor, accumulator width ÷ input width: 1, 2, 4 or 8. It selects the mnemonic: vmmacc.vv, vwmmacc.vv, vqwmmacc.vv or v8wmmacc.vv.
Test plan
One test_plan!{…} invocation in dsl_plans.rs. Not to be confused with an ACT testplan, which is a CSV file.
Section
A titled group of IR tests, for example "TC-MACC-01: Basic vmmacc.vv". One section becomes one emitted source file.
IR test
One configuration of one family, for example TC-MACC-01.e32.L1.m1.SS.V256. It has an action list and a vlen_guard.
Action
One IR step, for example TileLoadOp, Mmacc or Compare.
Golden model
The Rust code in gold/ that computes each expected value. It is independent of the code under test.
Lowering
How the backend renders the IME actions: asm (inline asm) or intrinsics (__riscv_* calls).
Verdict
The CI classification of one result against known-issues.txt: ok, known, skipped, UNEXPECTED, CHANGED, FIXED, MISSING, UNLISTED or STALE.

3Pipeline

Stage Module Input → output
Parse plan dsl_plans.rs, ime-test-gen-macros/ test_plan!{…} → TestPlan, built when the Rust crate compiles. The macro rejects unknown operations, mismatched input widths and W ∉ {1,2,4,8} at compile time.
Filter extensions.rs, main.rs --extensions and --test-pattern select subextensions and ID prefixes.
Expand expand_ir.rs, spec/, gold/ (VLEN × section) → IR tests, with golden arrays computed. Runs in parallel with rayon, then restores the original order.

The generated tree for VLEN=512 has 54 sections and 5372 tests, about 258 500 lines of C++. The static ELF is 39 MB. The generator takes 18.7 s to build in release mode. CI generates and compiles the sources for both lowerings in 88 s on 16 CPUs. run

4Test plan language

pub fn macc_int(vlens: &[u32]) -> TestPlan {
    let mut plan = test_plan! {
        vlen: [128, 256, 512, 1024],
        stride: tight,
        section "TC-MACC-01: Basic vmmacc.vv (C=0, positive)" {
            macc!("TC-MACC-01", e32, SS, zero, positive, sweep: all)
        }
        section "TC-MACC-09: vwmmacc (2x widening, all signs)" {
            macc!("TC-MACC-09", e16 x e16 -> e32, [SS, SU, US, UU], zero, positive, sweep: all)
        }
    };
    plan.vlens = vlens.to_vec();   // the macro cannot take runtime VLENs yet
    plan
}

Each line reads like one row of a specification table: the family ID, the formats (with widening written as e16 x e16 -> e32), the signedness, the C initialisation and the value generator. FP plans add frm: rne|rtz|rdn|rup|rmm|all and check_flags: true {{src:doc/dsl-reference.typ:39-240}}.

Code fact

sweep: all is parsed but its value is discarded. macc! and fmacc! always sweep. roundtrip! hard-codes vl_modes: [Min, Half] and stride_modes: [Tight, Padded]. code

5Expansion and sweeps

Expansion enumerates every legal combination. No values are random, and no RNG or seed exists anywhere in ime-test-gen/src. Integer inputs come from val = r·cols + k + 1 + offset, so every value is unique and a mismatch points to its source {{src:ime-test-gen/src/gold/integer.rs:93-118}}.

Integer MACC (TC-MACC) λ × LMUL at a fixed SEW and W, × signedness {SS, SU, US, UU} TC-MACC-09.e32.L1.m2.SU.V256

Rounding and stress (TC-RM, TC-RND, TC-SUB, TC-SPL) × rounding mode, adversarial values (ties, near overflow, subnormals, NaN, 0×∞, cancellation) TC-RM-F32.L1.m1.rtz.V256

6Intermediate representation

The IR is a JSON-serialisable list: sections → IR tests → actions {{src:ime-test-gen/src/ir.rs:13-251}}. --emit-ir writes it to stdout. All golden data is computed before the IR is written. For porting, the useful property is whether an action is target-neutral:

Category Actions Target-neutral?
Semantic IME operations TileLoadOp, TileStoreOp, TileZero, Mmacc, AccPair, AccUnpair Yes. Registers are named by role (A, B, C, CLo, CHi).
Data DeclareArray (values as i64), DeclareOutput Yes, apart from the C type names in ctype.
Vector state ConfigureVtype, AltfmtSetup, AltfmtClear, LambdaProbe Yes.
FP state SetFrm, RestoreFrm, ClearFflags, CheckFflags Yes.
Check Compare (Exact or FloatExact) Yes.
Raw code Asm, AsmBlock, FillRegs, ExtractRegs, CheckVtypeField No. They carry GCC inline-asm constraint strings and C literals.
Debug Dump Not needed in ACT.

The MACC families (integer and FP) use only target-neutral actions. The tile-only families (round trip, vstart, address check, tail check) still use raw Asm code. One IR test, abridged:

7Golden model

  • Integer. C[col·M+row] += Σk A·B, computed in i128 and truncated to the accumulator SEW. Overflow wraps; nothing saturates. Signedness reaches the hardware through altfmt_A and altfmt_B {{src:ime-test-gen/src/gold/integer.rs:45-87}}.
  • FP. FP uses a vendored arpfloat fork with OCP FP8 formats and FMA status flags.
    • Inputs are encoded with RNE (round-to-nearest-even).
    • Accumulation is sequential in k.
    • --fma rounds once, at an internal format: the accumulator format for W=1; f32 for inputs up to 16 bits with W>1; f64 otherwise.
    • The internal-format choice copies how QEMU evaluates widening FP mmacc {{src:ime-test-gen/src/expand_ir.rs:784-798}}.
  • Layout. The model computes C column-major. It then converts C to row-major, "to match vmts.v's output" {{src:doc/golden-model.typ:166-173}}.
  • Validation. Rust unit tests, plus agreement with QEMU in CI.
Spec versus convention

The documents say both FP modes conform to the specification, because rounding the partial sum is optional. A code comment says the FMA mode "does NOT match the spec … but matches some QEMU implementations" {{src:ime-test-gen/src/gold/fp_matmul.rs:164-165}}. CI uses --fma. The golden model is therefore tuned to QEMU. It is not a single specification-mandated rounding. --grouping reaches only the IR metadata; every golden call passes G=1 {{src:ime-test-gen/src/expand_ir.rs:799-811}}. code

8Backends and emitted code

Each IR test becomes one function, bool test_<id>(void). In the asm lowering, every IME action is one asm volatile statement on fixed registers. The function then compares element by element and calls record_pass or record_fail: 

if (effective_vlen() != 256u) { return true; }          // vlen_guard
const int32_t A_mem[8] = { 1, 2, 3, 4, 5, 6, 7, 8 };
const int32_t C_ref[64] = { 9, 10, 11, 12, 13, 14, 15, 16, 18, 20, … };
uint64_t vl_A_load = vtype_configure_vl(4, 1, 1, (uint64_t)8);
if ((int)vl_A_load < 8) { record_skip(…, "hardware VL too small"); return true; }
asm volatile ("vmtl.v v0, (%0), %1" : : "r"(A_mem), "r"((uint64_t)1) : "memory");
…
asm volatile ("vmmacc.vv v16, v0, v8" : :  : "memory");
asm volatile ("vmts.v v16, (%0), %1" : : "r"(C_result), "r"((uint64_t)8) : "memory");
for (int i = 0; i < 64; ++i) if (C_result[i] != C_ref[i]) { record_fail(…); pass = false; }
Bare-metal backend

The bare-metal backend is not exercised. No CI job or Makefile target builds it. Its header defines neither test_matches nor memcmp, yet every emitted test calls them. It includes vtype.h, which includes <stdio.h>. And emit_split always uses the hosted templates. It is not a ready starting point for ACT. code

9CI and verdicts

CI runs the same scripts on every VLEN from 128 to 32768:

  1. build.sh all
  2. run.sh basic
  3. run.sh gen … intrinsics
  4. run.sh gen … asm
  5. check.sh

run.sh never judges a result. check.sh gives every result a verdict against ci/known-issues.txt. A test that starts or stops failing turns CI red, and every SKIP must be listed. The model is Rust compiletest's known-bug {{src:ci/README.md:119-160}}.

I reproduced the CI job for VLEN=512 on moon-oxn-n04, with the pinned SDK image and the workflow's exact script calls: 

ci/tests/check-test.sh
ci/scripts/meta.sh "$R" "moon $SLURM_JOB_ID"
ci/scripts/build.sh all "$R/build"
ci/scripts/run.sh basic "$R"
ci/scripts/run.sh gen "$R" intrinsics
ci/scripts/run.sh gen "$R" asm
ci/scripts/check.sh "$R"
Block PASS SKIP CRASH Verdict

Result: PASS. Build: 88 s. Each run step: 3 s. The SDK is version 2026.10.14 with g++ (OpenChip-IME-f3ac260eca8f) 16.1.0 and qemu-riscv64 10.2.50. run

Environment notes
  • The SDK image has no make, and the compute nodes have no host make or cc. I added a GNU make build and built the generator on the login host. cargo needs a host linker.
  • The job also needs the CI scripts' positional arguments (the results directory, the runner label). Without them, every step exits with a usage error.

Trade-off

Pinning ACT to 608f08b7a drops 79 later ACT commits. Several of them matter for IME work:

  • 028fa67fb tests every vector instruction at every valid SEW.
  • 59dbb0114 stops vector builds when VLEN exceeds the generator limit.
  • 2be02e4c7 removes test workarounds for Sail limitations that 0.16 fixed (scontext, Ssdbltrp SDT). With the pre-0.15 fork, those suites at the ACT head may need the workarounds back.

The fork carries only 3 IME commits on top of its base (3eac5af4, 73911c38, efd0d7dc). Rebasing those 3 commits onto Sail 0.16 is smaller work than holding ACT back. It also makes the ACT head usable without a shim.

13Recommendation

  1. Unblock the reference model.
    • Rebase the IME Sail fork onto the 0.16 tag.
    • Fix the tile load/store indexing (Section 16).
    • Decide whether the IME extensions stay experimental.
    Without these steps, ACT's expected values for IME would be wrong or unbuildable.
  2. Bring up with option B. Check in the MACC IR for a chosen VLEN set, and import it with a testgen module. That module would be a production version of ir2act.py. This gives ACT runnable IME tests quickly. It also exercises the DUT configurations, wrappers and Sail.
  3. Keep the Rust golden model as a differential check. In the bring-up phase, compare each Sail signature with the Rust references, as crosscheck.py does. That comparison found the C-tile disagreement on its first run.
  4. Converge on option C. Express each sweep dimension as a coverpoint, for example cp_lambda, cp_lmul, cp_sew, cp_sign and cr_lambda_lmul, in testplans/Zvvmm.csv. Write a formatter that emits the tile-load, mmacc and tile-store sequence, and add covergroup templates for it. Coverage then shows which configurations a DUT run exercised. That is the ACT convention.
  5. Add UDB definitions. Define Zvvm and its subextensions in UDB, with a parameter for the supported λ set. Test headers can then use REQUIRED_EXTENSIONS: ['Zvvmm'] instead of V.
Why not option A as the target

Option A keeps two generator languages and puts Rust on ACT's critical path. ACT's conventions want the generator in testgen, discovered through registries, with the generated files checked in. Option B already gives the benefit of A, reuse of the sweep, without the build dependency.

16C-tile disagreement

Verdict

The Sail fork does not conform to the specification. QEMU and the Rust golden model do. The cause is in the fork's tile load and store, not in vmmacc.vv. The fork's vmtl.v and vmts.v address register elements with the flat index i. The specification requires tile_reg_idx(i, LMUL, λ, epr). code

What the specification says

The source is riscv/integrated-matrix-extension @ 6effbcae (2026-08-04), file src/integrated-matrix.adoc.

  • tile_reg_idx(i, LMUL, λ, epr) = (eil/λ)·epr + line·λ + eil%λ, where line = i/(λ·LMUL) and eil = i%(λ·LMUL) (lines 4249–4256).
  • mat_C_idx(i, j) = tile_reg_idx(i·N_max + j, EMUL_C, λ, epr_C) (lines 4259–4276).
  • vmtl.v and vmts.v both compute flat_idx = tile_reg_idx(i, LMUL, λ, epr) and mem_off = (i/linesize)·LD + i%linesize (lines 5925–5929 and 6055–6059). The store is therefore the exact inverse of the load.

Hand computation for TC-MACC-01 (VLEN 256, e32, λ=1, epr=8)

  1. Both loads run at LMUL=1, where tile_reg_idx(i,1,1,8) = i. So v0[i] = A[i] and v8[j] = B[j].
  2. The geometry is K_eff = 1, M = N_max = 8, EMUL_C = 8. C occupies v16–v23.
  3. mat_C_idx(i, j) = tile_reg_idx(8i+j, 8, 1, 8) = 8j + i, so element i of register v(16+j) holds A[i]·B[j].
  4. vmts.v at LMUL=8 with ld = 8 reads flat = (n%8)·8 + n/8 and writes mem_off = n. So C_mem[n] = A[n/8]·B[n%8].

Cause in the Sail fork

  • model/extensions/IME/ime_mem_insts.sail, lines 66–83: vmtl.v calls write_single_element(SEW, i, vd, …).
  • Line 145 of the same file: vmts.v calls read_single_element(SEW, i, vs3).
  • Both should index with ime_tile_reg_idx(i, LMUL, λ, VLEN/SEW). That helper exists at ime_utils.sail:98-106 and matches the specification.
  • The fork's vmmacc.vv (ime_mat_C_idx) also matches the specification.
  • The flat index came in with 3eac5af4. The later commit 73911c38 changed only the FP A/B indexing for W>1 and is not involved.

The bug is invisible when λ·LMUL = λ, which means LMUL=1. It is also invisible when a test loads and stores with the same geometry, because both sides then apply the same wrong mapping. The fork's first-party tests load tiles at LMUL=1. test_ime_vmmacc.S reads C back with vse32.v in flat register order (line 71), not with vmts.v. So no fork test runs vmts.v at LMUL>1. code Only a MACC result stored at LMUL>1 exposes the bug, and that is exactly what every C store in the MACC families does.

History
  • ca78f499 (2026-05-01) changed mat_C_idx from j·M+i to i·M+j, titled "C matrix is store in row-major order in VRs".
  • c52ee38a, the commit vtype.h cites, has the new SAIL code, but its prose still said "column-major register layout".
  • e9ce69a0, 7 minutes later, aligned the prose.

Since then the specification has been unambiguous. The Sail fork's output happens to equal the pre-ca78f499 layout, but it gets there through the load/store bug, not through mat_C_idx.

Consequence for ACT: an ACT build with the fork as reference model embeds wrong expected values for every MACC test with an accumulator LMUL above 1. A conforming DUT then fails those tests. Fixing lines 66–83 and 145 of ime_mem_insts.sail is the first item of the work plan.
