IME test generator: analysis and ACT integration

This report covers riscv-ime-arch-tests at commit 46f3781, which tests the RISC-V Integrated Matrix Extension (IME). It reuses the terms of Report 1. Evidence tags: run observed in a run, code read in the source, inferred deduced but not observed.

Summary

  1. The generator. ime-test-gen is a Rust generator.
    • A compile-time test plan language feeds an exhaustive sweep over legal configurations: VLEN × λ (lambda, the IME tile parameter) × LMUL × SEW × signedness or rounding mode.
    • An independent Rust golden model computes every expected value at generation time.
    • The output is self-checking C++, which runs under QEMU user mode on Linux.
  2. The suite passes its own CI here. At VLEN=512, with the pinned SDK image, the CI reproduction passed. The generator emits 5372 tests, and every result matched ci/known-issues.txt. run
  3. The main difference from ACT is the source of expected values. ACT takes them from Sail at build time, and the generators emit only inputs. ime-test-gen embeds its own golden values, which are tuned to match QEMU's rounding. ACT measures coverage with covergroups. ime-test-gen enumerates configurations and has no coverage model.
  4. The intermediate representation (IR) is the integration point. For MACC (matrix multiply-accumulate) tests, the IR uses only target-neutral operations: tile load, tile zero, mmacc, tile store and compare. My proof of concept, ir2act.py, converts that IR into ACT test files. ACT built them with the IME Sail fork as reference model, and they ran on two DUTs. run
  5. The proof of concept found a model disagreement.
    • With the Sail fork as DUT, all 6 test files pass.
    • With the SDK QEMU as DUT, all 6 fail.
    • QEMU and the Rust golden model agree with each other; the Sail fork stores the C tile transposed.
    • QEMU and the Rust golden model match the specification. The Sail fork's vmtl.v and vmts.v index register elements without tile_reg_idx.
    run code
  6. Recommendation.
    • Bring-up: import the IR into testgen (option B).
    • Target: port the tests to native ACT testplans and coverpoints (option C). Section 16b designs them, including tests that detect the Sail tile-index bug, which a round trip hides.
    • Throughout: keep the Rust golden model as a differential check against Sail.
    One blocker remains: the C-tile disagreement. A reproducer, a draft issue and a tested Sail patch are ready. The fix is not yet merged in the fork. A second draft issue covers the Sail fork's W>1 FP accumulation, which also contradicts the specification (Section 16b). The other blockers are resolved (Section 16a):
    • Sail version gate and schema: branch cgomez/0.16-plus-ime puts the IME commits on the 0.16 tag (Section 12a).
    • UDB extension definitions: an ACT UDB overlay defines the 65 IME extensions and the supported λ sets (d8e2f05ca).
    • Experimental-extension flag: ACT marks the IME extensions experimental and assembles them through .insn macros (24c90741c).
    • DUT configuration: config/ime/qemu-ime-rv64, with the SDK QEMU as DUT and the Sail fork as reference model (732f78d72).
  7. Source of truth. Since 2026-10-27, the IME specification decides every conflict, the IME Sail fork decides where the specification is silent or ambiguous, and QEMU, the SDK GCC and the Rust golden model never decide one (Section 16b).
Orientation

1Terms

These terms add to the glossary of Report 1. A test in ime-test-gen is not the same thing as an ACT test file. This report says "IR test" for the generator's unit.

IME, Zvvm
The Integrated Matrix Extension. Its subextensions are Zvvmm (integer matrix multiply-accumulate), Zvvfmm (floating-point), Zvvmtls (tile load and store) and Zvvmttls (transposing tile load and store). In the specification, Zvvm is the family name, not an extension name. Each of these four family extensions has type extensions, such as Zvvi32mm. The SDK compiler also accepts zvmma in -march; the specification does not define it.
λ (lambda)
The tile parameter held in vtype bits 62:60. Encoding 001 means λ=1, 010 λ=2, and so on up to 111 λ=64. The line size of a tile is λ·LMUL.
Tile
A matrix operand held in a vector register group. In the asm lowering: A in v0, B in v8, accumulator C in v16.
W
The widening factor, accumulator width ÷ input width: 1, 2, 4 or 8. It selects the mnemonic: vmmacc.vv, vwmmacc.vv, vqmmacc.vv or v8wmmacc.vv. The SDK GCC and ime-test-gen name the W=4 instruction vqwmmacc.vv (Section 18).
Test plan
One test_plan!{…} invocation in dsl_plans.rs. Not to be confused with an ACT testplan, which is a CSV file.
Section
A titled group of IR tests, for example "TC-MACC-01: Basic vmmacc.vv". One section becomes one emitted source file.
IR test
One configuration of one family, for example TC-MACC-01.e32.L1.m1.SS.V256. It has an action list and a vlen_guard.
Action
One IR step, for example TileLoadOp, Mmacc or Compare.
Golden model
The Rust code in gold/ that computes each expected value. It is independent of the code under test.
Lowering
How the backend renders the IME actions: asm (inline asm) or intrinsics (__riscv_* calls).
Verdict
The CI classification of one result against known-issues.txt: ok, known, skipped, UNEXPECTED, CHANGED, FIXED, MISSING, UNLISTED or STALE.

4Test plan language

pub fn macc_int(vlens: &[u32]) -> TestPlan {
    let mut plan = test_plan! {
        vlen: [128, 256, 512, 1024],
        stride: tight,
        section "TC-MACC-01: Basic vmmacc.vv (C=0, positive)" {
            macc!("TC-MACC-01", e32, SS, zero, positive, sweep: all)
        }
        section "TC-MACC-09: vwmmacc (2x widening, all signs)" {
            macc!("TC-MACC-09", e16 x e16 -> e32, [SS, SU, US, UU], zero, positive, sweep: all)
        }
    };
    plan.vlens = vlens.to_vec();   // the macro cannot take runtime VLENs yet
    plan
}

Each line reads like one row of a specification table: the family ID, the formats (with widening written as e16 x e16 -> e32), the signedness, the C initialisation and the value generator. FP plans add frm: rne|rtz|rdn|rup|rmm|all and check_flags: true doc/dsl-reference.typ:39-240.

Code fact

sweep: all is parsed but its value is discarded. macc! and fmacc! always sweep. roundtrip! hard-codes vl_modes: [Min, Half] and stride_modes: [Tight, Padded]. code

7Golden model

  • Integer. C[col·M+row] += Σk A·B, computed in i128 and truncated to the accumulator SEW. Overflow wraps; nothing saturates. Signedness reaches the hardware through altfmt_A and altfmt_B ime-test-gen/src/gold/integer.rs:45-87.
  • FP. FP uses a vendored arpfloat fork with OCP FP8 formats and FMA status flags.
    • Inputs are encoded with RNE (round-to-nearest-even).
    • Accumulation is sequential in k.
    • --fma rounds once, at an internal format: the accumulator format for W=1; f32 for inputs up to 16 bits with W>1; f64 otherwise.
    • The internal-format choice copies how QEMU evaluates widening FP mmacc ime-test-gen/src/expand_ir.rs:784-798.
  • Layout. The model computes C column-major. It then converts C to row-major, "to match vmts.v's output" doc/golden-model.typ:166-173.
  • Validation. Rust unit tests, plus agreement with QEMU in CI.
Spec versus convention

The documents say both FP modes conform to the specification, because rounding the partial sum is optional. A code comment says the FMA mode "does NOT match the spec … but matches some QEMU implementations" ime-test-gen/src/gold/fp_matmul.rs:164-165. CI uses --fma. The golden model is therefore tuned to QEMU. It is not a single specification-mandated rounding. --grouping reaches only the IR metadata; every golden call passes G=1 ime-test-gen/src/expand_ir.rs:799-811. code

Measured against the specification's (G, psm, rnd) model (spec:1361–1412), neither statement holds for every row. code run

  • W=1, same format: --fma computes roundfrm(C + a·b). That is G=1, psm=0, rnd=xct, which is legal. The default mode rounds the product to the C format first. That is G=1, psm=0, rnd=frm, which is also legal and is what Sail does.
  • W>1: both modes add each product into C on its own. The specification first reduces the W products of a sub-dot-product into one partial sum S (spec:1352–1359, 1386–1397). No (G, psm, rnd) tuple yields the per-product sequence. QEMU and Sail do the same.
  • --fma picks an f32 internal format for every input of up to 16 bits ime-test-gen/src/expand_ir.rs:792-798. For f16 or bf16 into f64 (TC-FQ-F16/BF16), the f64 accumulator is therefore rounded to f32 at each step. QEMU uses float64_muladd. The ones data hides the difference. inferred

8Backends and emitted code

Bare-metal backend

The bare-metal backend is not exercised. No CI job or Makefile target builds it. Its header defines neither test_matches nor memcmp, yet every emitted test calls them. It includes vtype.h, which includes <stdio.h>. And emit_split always uses the hosted templates. It is not a ready starting point for ACT. code

9CI and verdicts

CI runs the same scripts on every VLEN from 128 to 32768:

  1. build.sh all
  2. run.sh basic
  3. run.sh gen … intrinsics
  4. run.sh gen … asm
  5. check.sh

run.sh never judges a result. check.sh gives every result a verdict against ci/known-issues.txt. A test that starts or stops failing turns CI red, and every SKIP must be listed. The model is Rust compiletest's known-bug ci/README.md:119-160.

16C-tile disagreement

Verdict

The Sail fork does not conform to the specification. QEMU and the Rust golden model do. The cause is in the fork's tile load and store, not in vmmacc.vv. The fork's vmtl.v and vmts.v address register elements with the flat index i. The specification requires tile_reg_idx(i, LMUL, λ, epr). code

The specification is the source of truth (Section 16b), so the Sail fork is wrong. That QEMU and the golden model agree with the specification corroborates the verdict but does not decide it.

What the specification says

The source is riscv/integrated-matrix-extension @ 6effbcae (2026-08-04), file src/integrated-matrix.adoc.

  • tile_reg_idx(i, LMUL, λ, epr) = (eil/λ)·epr + line·λ + eil%λ, where line = i/(λ·LMUL) and eil = i%(λ·LMUL) (lines 4249–4256).
  • mat_C_idx(i, j) = tile_reg_idx(i·N_max + j, EMUL_C, λ, epr_C) (lines 4259–4276).
  • vmtl.v and vmts.v both compute flat_idx = tile_reg_idx(i, LMUL, λ, epr) and mem_off = (i/linesize)·LD + i%linesize (lines 5925–5929 and 6055–6059). The store is therefore the exact inverse of the load.

Hand computation for TC-MACC-01 (VLEN 256, e32, λ=1, epr=8)

  1. Both loads run at LMUL=1, where tile_reg_idx(i,1,1,8) = i. So v0[i] = A[i] and v8[j] = B[j].
  2. The geometry is K_eff = 1, M = N_max = 8, EMUL_C = 8. C occupies v16–v23.
  3. mat_C_idx(i, j) = tile_reg_idx(8i+j, 8, 1, 8) = 8j + i, so element i of register v(16+j) holds A[i]·B[j].
  4. vmts.v at LMUL=8 with ld = 8 reads flat = (n%8)·8 + n/8 and writes mem_off = n. So C_mem[n] = A[n/8]·B[n%8].

Cause in the Sail fork

  • model/extensions/IME/ime_mem_insts.sail, lines 66–83: vmtl.v calls write_single_element(SEW, i, vd, …).
  • Line 145 of the same file: vmts.v calls read_single_element(SEW, i, vs3).
  • Both should index with ime_tile_reg_idx(i, LMUL, λ, VLEN/SEW). That helper exists at ime_utils.sail:98-106 and matches the specification.
  • The fork's vmmacc.vv (ime_mat_C_idx) also matches the specification.
  • The flat index came in with 3eac5af4. The later commit 73911c38 changed only the FP A/B indexing for W>1 and is not involved.

The bug is invisible when λ·LMUL = λ, which means LMUL=1. It is also invisible when a test loads and stores with the same geometry, because both sides then apply the same wrong mapping. The fork's first-party tests load tiles at LMUL=1. test_ime_vmmacc.S reads C back with vse32.v in flat register order (line 71), not with vmts.v. So no fork test runs vmts.v at LMUL>1. code Only a MACC result stored at LMUL>1 exposes the bug, and that is exactly what every C store in the MACC families does.

History
  • ca78f499 (2026-05-01) changed mat_C_idx from j·M+i to i·M+j, titled "C matrix is store in row-major order in VRs".
  • c52ee38a, the commit vtype.h cites, has the new SAIL code, but its prose still said "column-major register layout".
  • e9ce69a0, 7 minutes later, aligned the prose.

Since then the specification has been unambiguous. The Sail fork's output happens to equal the pre-ca78f499 layout, but it gets there through the load/store bug, not through mat_C_idx.

Consequence for ACT: an ACT build with the fork as reference model embeds wrong expected values for every MACC test with an accumulator LMUL above 1. A conforming DUT then fails those tests. Fixing lines 66–83 and 145 of ime_mem_insts.sail is the first item of the work plan.

16bTestplan design (option C), 2026-10-27

This section designs native ACT testplans for the ime-test-gen plan (option C, work item 7). It is a design only: no ACT file is changed. Paths without a link are on the import branch at 732f78d72. The specification is integrated-matrix.adoc at 6effbcae, cited as spec: line numbers.

Source of truth (decided 2026-10-27)

When implementations or documents conflict, the IME specification decides. Where the specification is silent or ambiguous, the IME Sail fork decides. QEMU, the SDK GCC and the Rust golden model never decide a conflict.

  • Sail contradicts the specification: Sail is wrong. The bins follow the specification and stay in place, with no ignore_bins and no exclusion. Their expected values come from Sail, so they embed Sail's wrong values and fail on a conforming DUT until Sail is fixed. Each case has a Sail issue or work item. The tile-index bug and the W>1 partial sum are handled this way.
  • The specification permits several behaviours, for example rnd ∈ {frm, rto, xct}: tests do not depend on the choice.
  • The specification is silent: tests follow the Sail code, and the design records "spec silent; Sail behaviour" with a code citation.

FP rounding profiles

The specification (spec:1361–1478) splits the λ sub-dot-products of each LMUL=1 step into groups of G. A sub-dot-product holds W products. Each group is reduced to a partial sum S, either exactly (psm=0) or by a disclosed algorithm (psm=1). S is then rounded with frm (rnd=frm), rounded to odd (rnd=rto) or kept exact (rnd=xct). Last, C ← roundfrm(C + S). The implementation publishes one (G, psm, rnd) per (SEW, W, λ). That tuple covers every format combination of the geometry (spec:1456–1460). Legal values: G a power of two with 1 ≤ G ≤ λ; psm ∈ {0,1}; rnd ∈ {frm, rto, xct}. A psm=1 entry also needs the algorithm and a SAIL fragment (spec:1473–1502). Under the source-of-truth rule, a profile that fits a legal tuple is not a conflict, and tests must not depend on the tuple. A profile that fits no tuple violates the specification. In Sail it is a Sail bug; in QEMU or the Rust model it is a finding only.

Value patterns

  • Integer accumulation wraps modulo 2SEW (spec:1112), so random data is exact. A ramp bin keeps the ime-test-gen positional values.
  • FP: with G=1, every group is one sub-dot-product of W products. The target's psm and rnd are not disclosed. The specification permits psm ∈ {0,1} and rnd ∈ {frm, rto, xct} (spec:1376–1460), so by the source-of-truth rule the data gives the same result for every permitted choice. The random and edge data also keep every running C value exact, so they do not see the per-product accumulation of Sail and QEMU. cp_fp_subdot targets that deviation on purpose (Section 16b, W>1 partial sum).
  • Random FP data (exact_dot_rng, after unordered_sum_rng in generators/testgen/src/testgen/formatters/types/fvvsr_type.py:62-74): small integers whose products, partial sums and running C values are all exact in the C format. Every rnd then returns S unchanged. Under psm=1 the reduction is implementation-specific (spec:1397); exactness must be checked against the disclosed algorithm. inferred
  • Edge data has one nonzero product p per C element, so S = p. Special values (NaN, ∞, ±0, 0×∞) are portable. For ties, overflow, underflow, inexact and the frm sweep, p is exact in the C format, and C₀ is chosen so that the final roundfrm(C₀ + p) rounds. That final rounding is common to every profile. The other products of the element are zero, for every W.
  • The exact-sum design follows from the rule. The signature comes from Sail, which is rnd=frm, and the SDK QEMU is rnd=xct. Both are permitted. A W=1 testcase with an inexact product would depend on that choice, so the data excludes it. inferred
  • Multi-term tests that only need the specification's S are no longer deferred: cp_fp_subdot covers them now and fails until the Sail fix (work item 10).
  • Tests whose result depends on the (G, psm, rnd) choice, such as inexact products, cancellation across k and accumulation order, wait for the target's disclosure. They then need overlay parameters and a Sail profile selected from sail.json (step 8).
